# Чек-лист передачи разработчику

## Что передано

- живой интерактивный референс;
- исходники текущего прототипа;
- точное ограничение этапа 1;
- структура меню;
- описание главной страницы;
- рекомендуемая структура Laravel;
- критерии приёмки;
- список решений для следующих этапов.

## Что попросить у разработчика в ответ

- ссылку на тестовое окружение Laravel;
- короткое видео мобильного меню;
- скриншоты главной на десктопе и телефоне;
- список изменённых Laravel-файлов;
- список мест, где пока используются демонстрационные данные;
- подтверждение, что остальные разделы являются заглушками.

## Проверка после каждого шага

### Layout

- ширина и отступы близки к референсу;
- боковая панель фиксирована;
- верхняя панель не перекрывает контент;
- фон, карточки и акцентные цвета совпадают по характеру.

### Navigation

- все пункты открываются;
- активное состояние соответствует URL;
- мобильное меню закрывается после выбора;
- пункты идут одним списком.

### Dashboard

- четыре показателя;
- список последних заказов;
- график 7/30 дней;
- быстрые действия;
- «Старт магазина» с обязательными и необязательным шагом;
- есть пустые состояния.

### Responsive

- нет горизонтального скролла;
- меню удобно нажимать;
- карточки складываются в одну колонку;
- всплывающие элементы не выходят за экран.

## Что не принимать в рамках этапа 1

- полную карточку товара;
- менеджер вариантов;
- редактор категорий;
- редактор витрины;
- обработку заказов;
- реальные настройки доставки и оплаты;
- шаблоны товаров;
- любые новые функции, которых нет в ТЗ.

Если разработчик хочет начать с них раньше, сначала нужно завершить и принять каркас. Иначе каждый последующий экран придётся адаптировать повторно.

## Формат обратной связи

Ошибки лучше фиксировать коротко:

```text
Экран:
Разрешение:
Что происходит:
Как должно быть:
Ссылка или скрин:
```
